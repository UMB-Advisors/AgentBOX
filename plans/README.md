## Findings considered and rejected (do not re-audit)

- **`/api/env/reveal` rate-limiter "race"** (hermes_cli/web_server.py:2570) —
  handler is `async def` with no awaits between the check and the append;
  atomic on the event loop. Not a bug.
- **`clear-send-attempt` attestation "parsed but unused"** — the zod schema
  is `verified_in_gmail_sent: z.literal(true)` (lib/schemas/drafts.ts:116);
  validation itself enforces it. By design.
- **"Upgrade google_calendar OAuth scope for v2"** — already shipped in
  MBOX-460 (`lib/oauth/google.ts:74` requests `calendar.events`). Stale.
- **Kysely JSON-path CVE (GHSA-pv5w-4p9q-p3v2)** — was not present in
  `npm audit --omit=dev` on the original lockfile (2026-06-11 AM), but
  **resurfaced as HIGH after plan 006's lockfile regeneration** (same day).
  The original audit finding was right. Follow-up: bump kysely and scan for
  user-controlled `.key()`/`.at()` JSON-path calls.
- **Google OAuth callback error-parameter "reflection"**
  (web_server.py:1531) — the value passes through `urlencode` in
  `_google_settings_redirect` (:1488); no parameter injection. Attacker
  controls display text only. Cosmetic; not planned.
- **Calendar/OAuth "error swallowing"** — largely by-design: the code
  discriminates `token_expired`/`rate_limited`/`fetch_failed` and throws
  typed `OAuthTokenError`. The surviving sliver (refresh-on-401 retry) was
  plan 011, investigate-first — **resolved 2026-06-11 as moot**:
  `getAccessToken` (lib/oauth/google.ts:482) refreshes on every call, so each
  calendar fetch uses a seconds-old token; a 401 there means a revoked
  refresh token, which the `token_expired` → reconnect path models correctly.
- **systemd boot-race hermes-gateway vs compose stack** — MED-confidence,
  theoretical; recovery via RestartSec works. Revisit only if cold-boot
  errors are observed in the field (then verify against
  systemd/hermes-gateway.service ordering).
- **n8n credential re-import idempotency on installer re-run** —
  MED-confidence, depends on n8n import semantics; deferred. Worth a guard
  only if a repair-run incident occurs.
- **WhatsApp QR pairing automation** — documented as an intentional manual
  step (STATE v1.2.0, RUNBOOK covers re-pairing). Not a gap.
- **factory-*.sh duplication across mailbox/scripts and vendor lineage** —
  real smell, MED confidence, but consolidation needs a vendor-submodule
  audit; explicitly deferred (noted in plan 009's maintenance section).
