Why we built it

Two forces pushed the AI off the cloud and onto a box.

Privacy

An email assistant means handing a vendor your entire inbox. For the customers we target, that's a non-starter. Content has to stay on hardware they own.

Economics

Routing every inference to the cloud is a recurring per-seat bill. A ~$500 one-time board beats 12 months of cloud escalation — the margin only works on hardware.

So the design target was fixed up front: the agent, its memory, and the pipeline all run on one local box. No cloud account required to operate it.

[0:45–2:15] WHY — 90s. Two forces: privacy (the felt one) and unit economics (the structural one). Land the thesis: this is an appliance, not a service. That single choice is what makes the rest hard — which is the next slide.

How it works · one email, end to end
Inbound (Gmail) — n8n polls every 5 min, dedupe by message_id, ingest
▼   classify (Qwen3-4B @ 4096 ctx, local)   ▼
conf ≥ 0.75 + routine → LOCAL draft (Qwen3 + sender-scoped RAG)
conf < 0.75 / escalate → CLOUD draft (gpt-oss:120b)
▼   draft lands in queue, status = pending   ▼
Human approves — edit / approve / reject in the dashboard (no autonomous send)
▼   CAS lock on send_attempt_at (idempotent)   ▼
Gmail Reply — thread-preserved, then outbound is embedded back into RAG
[5:30–7:30] THE FLOW — 2 min. Walk ONE email top to bottom. Hit the design choices: (1) classify locally first; (2) confidence-gated routing — local for routine, cloud only for the uncertain tail; (3) RAG is SENDER-SCOPED (don't answer Alice with Bob's history); (4) human-in-the-loop is a hard rule; (5) the send is idempotent via a CAS lock so a retry can't double-send.

What broke first

Two ollama instances + a second runtime → contention on the shared pool → 138 container restarts in one soak window (CUDA alloc failures, not clean OOM).

How we fixed it

Consolidate to one ollama for both draft + embeddings. Add a preflight: any backfill checks MemAvailable ≥ 1.5 GiB or it refuses to run.

[7:30–9:30] WAR STORY 1 — 2 min. The headline engineering result. Read the table: even worst case (local model drafting WHILE the agent runs a heavy turn) left 1.8 GB free — ~3.6× our 500 MB safety bar. Then the failure: dual runtimes caused 138 restarts — not clean OOM kills, CUDA-side alloc failures cascading into restart loops. Fix: one ollama + a memory preflight guard so backfills can't stampede the pool. This is the "every byte matters" proof.
Engineering problem 2 · the model & context tradeoff

A 4B model can't reason in a 64K window.

  • Qwen3-4B @ 4096 ctx — the Goldilocks point: deep enough to see the email + persona, shallow enough that KV cache doesn't blow latency
  • Hermes 0.16 enforces a ≥64K context floor → KV cache exceeds the model weights → OOM / timeout on 4B
  • So we pin Hermes to v0.15.1 and accept 4096
# custom Modelfile — never the bare alias
FROM qwen3:4b-instruct
PARAMETER num_ctx 4096

# consequence: injected memory is
# token-budgeted into the 4096 window
4096 - email(~200) - draft(~200)
     - memory(capped) = reasoning room

Footgun fixed: the bare qwen3:4b alias silently flipped to a thinking variant emitting scratchwork instead of clean JSON. Pin the digest.

[9:30–11:15] WAR STORY 2 — 105s. The version-pin nobody expects. 0.16 sounds like an upgrade but its 64K context floor is incompatible with a 4B model — the KV cache alone would exceed the weights. So we pin 0.15.1 and live at 4096. Consequence: every injected memory token steals from reasoning room, so memory recall is hard-capped + word-safe truncated. The footgun (bare alias flipping to a thinking model that emitted scratchpad noise instead of JSON) is a great "pin your model digests" lesson.
Engineering problem 3 · local vs cloud routing

Confidence decides where the work runs.

route(email):
  spam_marketing            → drop            # no draft at all
  confidence < 0.75          → CLOUD           # safety net for the uncertain tail
  reorder|scheduling|...    → LOCAL (Qwen3-4B) # routine, drafts well on-device
  escalate|unknown          → CLOUD (gpt-oss:120b)

The classifier's top-1 probability is the lever. Below 0.75, a misdraft costs more than a ~$0.001 cloud call — so we pay it. Above it, routine mail stays 100% on-device. Threshold tuned on the live customer dataset.

[11:15–12:45] WAR STORY 3 — 90s. The cost/quality dial. Key insight: use the classifier's own confidence as the router. Cheap, routine, high-confidence mail drafts locally (free, private). The long tail — low confidence, unusual categories — goes to a 120B cloud model. 0.75 was tuned empirically, not picked from the air. Result: most volume never leaves the box; you only pay cloud for the cases where being wrong is expensive.
Engineering problem 4 · the deploy race
The incident · 2026-06-09
  • Two agents, one box. deploy did rsync --delete with no lock, no freshness check
  • A peer built stale code and overwrote a fresh deploy — silently reverted a shipped feature
  • Client-side reload meant nobody noticed for hours
The fix · structural, not discipline
  • git freshness — refuse if HEAD is behind origin/main
  • flock per-box deploy lock — one deployer at a time
  • DEPLOY_META provenance stamp — forward-only guard
  • CI is the deployer — self-hosted runner, merge-to-main only

Lesson: "be careful when you deploy" is not a control. Make the unsafe path impossible.

[12:45–14:15] WAR STORY 4 — 90s. The ops war story engineers love. A shared appliance + a last-writer-wins rsync = a peer's stale build silently reverted a feature, undetected for hours because the dash reloads client-side. The fix isn't a wiki rule — it's four structural guards ending in CI-as-deployer so the only way to ship is merge-to-main. "Make the unsafe path impossible" is the takeaway.
